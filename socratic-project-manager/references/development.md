# 开发项目：按实际项目选用的追问方向

这些方向用于发现遗漏，不是逐条发给用户的固定问卷。先理解当前流程，再问会改变产品行为的取舍。

| 方向 | 通俗切入点 | 回答应确定什么 |
|---|---|---|
| 目的与首版 | 最近一次做这件事怎么做？第一版只解决一件事，你选什么？ | 真实问题、使用场景、首版边界、成功标准 |
| 使用者与协作 | 谁能看、谁能改？两个人同时改同一条内容怎么办？ | 角色、权限、协作冲突；单人使用可跳过协作机制 |
| 输入输出 | 现在交给系统的材料长什么样？最后要拿到什么？ | 已有格式、真实样例、交付格式、与旧流程的衔接 |
| 数据行为 | 缺一列、重复一条、文件坏了时，你希望怎样处理？ | 校验、错误反馈、纠错与原件保护 |
| 自主性 | 哪些决定可以自动做？哪些改变会让你不放心？ | 自动操作范围、人工决策点、例外处理 |
| 质量与规模 | 一次通常处理多少？等待多久会影响你的工作？ | 规模、响应预期、可测量的验收条件 |
| 故障与续跑 | 做到一半关机了，最不能丢的是什么？ | 恢复、重试、重复操作的处理；按必要程度设计 |
| 变更与兼容 | 换版本后，以前的数据或工作方式必须继续可用吗？ | 迁移范围、兼容性、回退与验收 |
| 部署与维护 | 谁来安装、更新、处理报错？已有设备有什么限制？ | 实际运行环境、维护责任、交付方式 |

代码已有答案时先读代码；用户决定期望行为，agent 判断哪些现状可以复用。核实库版本、平台能力等易变化事实后再依赖它们，不拿猜测作技术承诺。

提出技术方案时，把技术选择连到用户的实际约束，例如“多人同时编辑，所以需要解决覆盖冲突”；不要把已有技术选型当成用户需要回答的新题。接口只细化到执行者能正确连接输入输出；简单工具不强加账号、服务器或数据库。

验收写成具体场景：给定什么输入，做什么动作，观察什么结果，失败时怎样显示和保留原件。性能阈值和成本上限来自用户或明确授权建议；没有测量时不要承诺必达。
